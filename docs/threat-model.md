# Threat model (living document → becomes security-assessment.md)

| # | Threat | Vector | Mitigation | Test | Status |
|---|---|---|---|---|---|
| T1 | Prompt injection via documents | Invoice notes / descriptions instruct agent to pay | Untrusted text wrapped as data; `schedule_payment` takes only counterparty id + payable invoice id (no payee name / bank details), pays stored details only; gate DENIES non-allowlisted payee, invoice not an open payable of that counterparty, or amount > invoice outstanding | A1 (incl. injection mapped onto QuickShip: $4,650 vs QS-2291 $465 → DENY); `test_gate.py`, `test_action_service.py`; `test_llm_classifier.py`; `test_agent_a1.py` | mitigated — gate (Phase 3): `policy/gate.py` DENIES non-counterparty/non-allowlisted payee, invoice not an open payable of that payee, amount > outstanding (bank + sandbox payments), a payment date outside [DEMO_TODAY, +90 days], and any extra param (`extra="forbid"`: no payee name, beneficiary or account field exists); every denial is an audited `denied` Action, never REQUIRE_APPROVAL. Reminder drafts are a fixed template over structured fields only (`services/drafts.py`), recipients are the stored `contact_email`; a draft is refused once its amount differs from the current outstanding or it is older than the cooldown. Inputs that cannot be stored/hashed (NaN/Infinity, lone surrogates) are refused before any write, and 422 responses never echo submitted values. Agent side (Phase 4): the system prompt is a constant filled only with Business/User fields (`agent/prompts.py`); invoice notes, line descriptions and bank descriptions reach the model only inside tool results as `{"untrusted_text", "source", "instruction_like"}` wrappers, cleaned (control chars removed, ≤600 chars, `[[`/`]]` and PII-token brackets neutralised so a document cannot forge a citation or token); invoice lists never include notes; figures inside untrusted text never count as evidence; EXECUTE tool inputs go to the gate unfiltered, so an injected beneficiary/account field becomes an audited `denied` Action (A1 test: four forced variants all DENIED, never proposed). Hardening after the Phase 4 jailbreak review: zero-width and bidi control characters (Unicode Cf) are stripped from untrusted text and from chat messages before masking, the `instruction_like` check and the model; `dispatch` checks the caller's role before anything is proposed or stored (viewers cannot create Actions at all, accountants cannot propose payments or loans); at most 3 EXECUTE proposals per turn (approval fatigue). Residual: the agent's free-text rationale stored on a proposal is LLM output and may echo injected text. The Phase 5 approvals inbox shows it under "Why the assistant proposes this" with a note that it is the assistant's own wording and may quote documents, and puts the amount, payee, invoice and outstanding balance next to it from the stored params and records (`services/action_display.py`), never from the rationale; contact email addresses are never sent to the browser (`tests/test_api_approvals.py`). Phase 1 categorizer: system prompt is a fixed constant; descriptions reach the LLM only as normalized `[A-Z0-9 ]` text inside a JSON array, reply is schema-constrained and re-validated, rules always win over the LLM; ingestion never creates counterparties from description text. Phase 2 engine: `engine/snapshot.py` never loads invoice `notes`, so forecast/what-if cannot be steered by them (`test_invoice_notes_never_affect_the_forecast`) |
| T2 | Agent executes without consent | LLM calls EXECUTE tool | EXECUTE only creates `proposed` Action; agent has no approve tool; human approval via authenticated API | `test_action_service.py`; `test_agent_tools.py` | mitigated — `services/action_service.py` is the only executor: EXECUTE tools become `proposed` Actions, run only after `approve` by an authorized human, gate re-checked at execution; agent actors carry the signed-in user's role (`agent:user:<id>`). Phase 4: the tool registry takes tiers from `policy/tiers.TOOL_TIERS`; EXECUTE tools have no handler and only call `ActionService.propose` (agent actor, idempotency key per conversation + params), returning `proposed`/`denied`; there is no approve tool; tools offered to the model are filtered by role and the gate re-checks every call; the answer check flags any past or perfect-tense claim that an action was sent/went out/paid/scheduled/approved/executed/completed/done (only a negation right next to the verb excuses it) unless a tool result in this turn said `executed` |
| T3 | Excessive payment | Agent or user requests large transfer, or splits one into several | `max_single_payment` ($5,000) and cumulative `max_daily_payments` ($10,000 per payment date: executed + approved-pending) → DENY; amount ≤ invoice outstanding | A2 (`test_gate.py`, `test_action_service.py`) | mitigated — $9,000 → DENY; two $4,000 payments on one date pass, a third → DENY at proposal or at the execution re-check (migration 0005); amounts are strict integer cents > 0; two approved part-payments cannot exceed the invoice; loan products are capped cumulatively (earlier applications count). The daily cap is per scheduled payment date (dates limited to DEMO_TODAY … +90 days); across all dates, total payable is bounded by the outstanding balances of open payable invoices, since every payment must reference one |
| T4 | Privilege escalation | Viewer/accountant approves restricted action | RBAC checks on every route + gate | A3 (`test_api.py`, `test_action_service.py`, `test_security_review.py`) | mitigated — viewer approve/reject → 403 + audited `approval_forbidden`; Phase 5 recategorize (`POST /transactions/{id}/category`, `services/categorization.py`): owner/accountant only (viewer → 403 + audited `recategorize_forbidden`), audited `transaction_recategorized`, and it writes only the transaction's categorization (category, `category_source = human`, `needs_review = false`) plus one human CategoryRule, then recomputes series, forecast and insights without touching counterparty stats; a test snapshots every gate input (counterparties incl. `is_allowed_payee`, invoices and lines, policy, actions, sandbox rows, every non-category transaction column, invoice outstanding balances) before and after and checks the A1 payment is still denied (`tests/test_api_transactions.py`); accountant may approve reminders only; owner-only tools from `Policy.require_owner_for`; role and business re-read from the DB on every request; actions, drafts, invoices, accounts and the `/audit` event list are scoped to the caller's business. The hash chain itself is global (one sequence per deployment), so `/audit/verify` reports deployment-wide integrity; multi-company is out of scope (SPEC §2). Refusals (not found, wrong role, bad input, idempotency conflict) are audited |
| T5 | Duplicate execution | Retries / double clicks | Idempotency key, unique constraint | A4 (`test_action_service.py`) | mitigated — re-approve/re-execute of an executed Action returns its original result (audited `execute_replayed`); reused idempotency key returns the same Action, a reused key with different tool/params is a 409 (keys unique per business, migration 0004); approve/reject/execute lock and re-read the Action (`SELECT … FOR UPDATE`), so a concurrent second decision sees `executed` and replays instead of overwriting it; `sandbox_*.action_id` UNIQUE rejects a second write |
| T6 | Log tampering | DB edit to hide action | Hash-chained AuditEvent + verify; append-only in ORM and DB | A5 (`test_audit.py`) | mitigated for app-level and SQL-client tampering — `hash = sha256(prev_hash + canonical_json(event))` (ASCII, strict JSON); `verify_chain` reports the first broken seq for an edited, deleted or individually re-hashed row; migration 0003 trigger rejects UPDATE/DELETE on Postgres and SQLite; appends serialized with a Postgres advisory lock. Not mitigated against a DB owner who can drop the trigger: see residual risks — Phase 7 anchors the head hash outside the DB |
| T7 | Hallucinated numbers | LLM invents figures | All numbers from engine tools; citations required | `test_citations.py`, `test_agent_runner.py`, live smoke; `test_forecast.py` | mitigated — every ForecastLine carries source_ids that resolve to real records (account/invoice/recurring_series/transaction); integer cents only; Phase 4: tool results carry integer `*_cents` plus server-formatted `*_display` text and a `ref` per record; `agent/citations.py` checks every `[[type:id]]` (known type, exists in the user's business, actually returned by a tool in this conversation) and every money/percent figure (cited in its sentence, and carried by one of those citations); one automatic rewrite, then the answer is shown with invalid chips marked and a visible "could not be verified" notice, audited `agent_citation_failed`. Hardening: values someone supplied rather than the engine derived — what-if scenario inputs and their per-week change, action params and rationales (`supplied_input`) — are shown to the model but never count as evidence; what-if inputs are capped (≤ $1,000,000, dates and delays within the 13-week horizon); a figure found only in document text is accepted only when explicitly quoted (inside quotation marks or after "the note says …" in the same sentence); money is also recognised as `USD 1,234`, `1,234 dollars` and fullwidth `＄` (text NFKC-normalised). Residual: the check matches figures, not the meaning of the sentence around them; bare numbers (day/week counts, quantities) are not checked; what-if outputs (closing balances, gap) are engine-derived but follow from the scenario the model chose, so a what-if chip proves a simulation, not a fact |
| T8 | PII leakage to LLM | Account numbers/emails in prompts | `pii.py` masking before LLM calls | `test_pii.py`, `test_agent_a1.py` | mitigated — categorizer sends only normalized descriptions (card numbers, terminal IDs, phones, refs stripped) + direction, no amounts or DB ids (`test_llm_classifier.py`); Phase 4 agent: `agent/pii.py` masks IBANs, card and account numbers, emails and phones in every string of every tool result, user message and tool input (ints untouched) into per-conversation tokens; contact emails are never put in tool results; unmasking happens only on the final text shown to the signed-in user; audit payloads and stored rationales keep the masked form; the A1 test asserts QS-2291's account number never appears in any model request. Residual: regex-based; see residual risks for formats that are not caught |

| T10 | Abuse of chat endpoint | Spamming / cost | Rate limit per user | `test_chat_api.py` | mitigated — `POST /chat`: 10 turns per minute and 100 per day per user, counted from `agent_turn_started` audit events (durable, multi-worker safe), 429 + `Retry-After` + audited `chat_rate_limited`; one turn in flight per user; message ≤ 4,000 chars; ≤ 8 model calls per turn (the last with tools disabled), ≤ 4,096 output tokens per call; conversations are server-side only (2 h, ≤ 30 turns), so a client cannot inject forged history. Hardening: rate limit and role are checked before a conversation is created, so refused requests leave nothing behind; conversations are capped per user (20, a user only evicts their own); the in-flight lock is released when the response ends for any reason, including a disconnect before streaming starts; refusal audit events are capped at 5 per user per minute, then one `chat_refusals_suppressed` summary; `agent_turn_started` records the PII-masked message (≤ 500 chars) so jailbreak attempts are reviewable. ## Known residual risks (be honest in the report)
- Demo auth (JWT, seeded users) is not production-grade identity: lockout is per email only (no per-IP limit, so a known email can be locked out on purpose), no token revocation before expiry (8 h).
- Demo credentials are public by design: the seeded owner, accountant and viewer accounts share one published password (`seed/load.py`), and the deployed demo shows one-click sign-in so judges can try every role. This is acceptable only because of what those accounts can reach: every effect is sandbox-only (payments, emails and loan applications are rows in Sandbox* tables; nothing touches a real bank, inbox or lender), all data is fictional, and the daily AI budget (`DAILY_LLM_BUDGET_USD`, T10) caps what anyone can spend through the assistant, with per-user chat rate limits on top. What remains is vandalism of the demo state (approving or rejecting the planted actions); the Phase 7 demo reset restores it. Never reuse this setup with real data or real integrations.
- LLM categorization can still mislabel; mitigated by confidence threshold + human review, not eliminated.
- Forecast is heuristic (historical behavior); not a guarantee.
- Audit chain: the hash is unkeyed, so someone able to drop the trigger (DB owner) can edit any event and recompute every later hash, or delete the newest events, and `/audit/verify` still passes. Planned mitigation: Phase 7's evidence export (`python -m app.sandbox.evidence_export`) writes the latest seq + hash outside the DB; verifying against that anchor detects any rewrite or truncation before it.
- `Policy.payee_allowlist_mode` is stored but not read: the gate always behaves as `strict` (only `is_allowed_payee` counterparties), which is the safe setting.
- PII masking (`agent/pii.py`) is regex-based and misses some formats: dashed account numbers (`000-123-456-789`), lowercase or dashed IBANs, fullwidth-@ and `[at]`/`[dot]` emails, phones like `555 0100 9999`, routing numbers with dashes. Zero-width-split numbers are caught (Cf characters are stripped first). Masking is a backstop: the agent never needs account details, payments use stored counterparty details only.
- Counterparty names, invoice numbers and SKUs reach the model and the reminder/terms templates unwrapped (not as `untrusted_text`). Today they come only from seed data, so they are not attacker-controlled; once invoice or counterparty upload exists they become an injection path and must be wrapped (model) and validated (templates).
- The agent's citation check covers money and percentages only; day/week counts and other bare numbers are not verified against records.
- Streamed chat text is shown before the citation and claim checks finish. The Phase 5 UI shows it only as a marked draft and replaces it with `done.message` (T13); a different client that renders the raw stream would not get this protection.
- The login page's one-click demo accounts read `DEMO_PASSWORD` from the frontend's environment and put it in the page; set it only on demo deployments (the seeded password is already public demo data).
- The categorizer can run on a cheaper model (`LLM_MODEL_CLASSIFIER`, e.g. Haiku); it may be less confident, which sends more transactions to the human review queue rather than mislabelling them (confidence < 0.7 → review).
- Financing catalog is simulated, not real offers. Every ranking carries a "not financial advice" disclaimer (`engine/financing.py`); options are suggestions only and nothing executes without an approved Action.
