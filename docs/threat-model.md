# Threat model (living document → becomes security-assessment.md)

| # | Threat | Vector | Mitigation | Test | Status |
|---|---|---|---|---|---|
| T1 | Prompt injection via documents | Invoice notes / descriptions instruct agent to pay | Untrusted text wrapped as data; `schedule_payment` takes only counterparty id + payable invoice id (no payee name / bank details), pays stored details only; gate DENIES non-allowlisted payee, invoice not an open payable of that counterparty, or amount > invoice outstanding | A1 (incl. injection mapped onto QuickShip: $4,650 vs QS-2291 $465 → DENY); `test_gate.py`, `test_action_service.py`; `test_llm_classifier.py`; `test_agent_a1.py` | mitigated — gate (Phase 3): `policy/gate.py` DENIES non-counterparty/non-allowlisted payee, invoice not an open payable of that payee, amount > outstanding (bank + sandbox payments), a payment date outside [DEMO_TODAY, +90 days], and any extra param (`extra="forbid"`: no payee name, beneficiary or account field exists); every denial is an audited `denied` Action, never REQUIRE_APPROVAL. Reminder drafts are a fixed template over structured fields only (`services/drafts.py`), recipients are the stored `contact_email`; a draft is refused once its amount differs from the current outstanding or it is older than the cooldown. Inputs that cannot be stored/hashed (NaN/Infinity, lone surrogates) are refused before any write, and 422 responses never echo submitted values. Agent side (Phase 4): the system prompt is a constant filled only with Business/User fields (`agent/prompts.py`); invoice notes, line descriptions and bank descriptions reach the model only inside tool results as `{"untrusted_text", "source", "instruction_like"}` wrappers, cleaned (control chars removed, ≤600 chars, `[[`/`]]` and PII-token brackets neutralised so a document cannot forge a citation or token); invoice lists never include notes; figures inside untrusted text never count as evidence; EXECUTE tool inputs go to the gate unfiltered, so an injected beneficiary/account field becomes an audited `denied` Action (A1 test: four forced variants all DENIED, never proposed). Residual: the agent's free-text rationale stored on a proposal is LLM output and may echo injected text; the approvals UI must show it as the agent's reasoning next to the gate-checked parameters. Phase 1 categorizer: system prompt is a fixed constant; descriptions reach the LLM only as normalized `[A-Z0-9 ]` text inside a JSON array, reply is schema-constrained and re-validated, rules always win over the LLM; ingestion never creates counterparties from description text. Phase 2 engine: `engine/snapshot.py` never loads invoice `notes`, so forecast/what-if cannot be steered by them (`test_invoice_notes_never_affect_the_forecast`) |
| T2 | Agent executes without consent | LLM calls EXECUTE tool | EXECUTE only creates `proposed` Action; agent has no approve tool; human approval via authenticated API | `test_action_service.py`; `test_agent_tools.py` | mitigated — `services/action_service.py` is the only executor: EXECUTE tools become `proposed` Actions, run only after `approve` by an authorized human, gate re-checked at execution; agent actors carry the signed-in user's role (`agent:user:<id>`). Phase 4: the tool registry takes tiers from `policy/tiers.TOOL_TIERS`; EXECUTE tools have no handler and only call `ActionService.propose` (agent actor, idempotency key per conversation + params), returning `proposed`/`denied`; there is no approve tool; tools offered to the model are filtered by role and the gate re-checks every call; the answer check flags any claim that something was sent/paid/executed unless a tool result said `executed` |
| T3 | Excessive payment | Agent or user requests large transfer, or splits one into several | `max_single_payment` ($5,000) and cumulative `max_daily_payments` ($10,000 per payment date: executed + approved-pending) → DENY; amount ≤ invoice outstanding | A2 (`test_gate.py`, `test_action_service.py`) | mitigated — $9,000 → DENY; two $4,000 payments on one date pass, a third → DENY at proposal or at the execution re-check (migration 0005); amounts are strict integer cents > 0; two approved part-payments cannot exceed the invoice; loan products are capped cumulatively (earlier applications count). The daily cap is per scheduled payment date (dates limited to DEMO_TODAY … +90 days); across all dates, total payable is bounded by the outstanding balances of open payable invoices, since every payment must reference one |
| T4 | Privilege escalation | Viewer/accountant approves restricted action | RBAC checks on every route + gate | A3 (`test_api.py`, `test_action_service.py`, `test_security_review.py`) | mitigated — viewer approve/reject → 403 + audited `approval_forbidden`; accountant may approve reminders only; owner-only tools from `Policy.require_owner_for`; role and business re-read from the DB on every request; actions, drafts, invoices, accounts and the `/audit` event list are scoped to the caller's business. The hash chain itself is global (one sequence per deployment), so `/audit/verify` reports deployment-wide integrity; multi-company is out of scope (SPEC §2). Refusals (not found, wrong role, bad input, idempotency conflict) are audited |
| T5 | Duplicate execution | Retries / double clicks | Idempotency key, unique constraint | A4 (`test_action_service.py`) | mitigated — re-approve/re-execute of an executed Action returns its original result (audited `execute_replayed`); reused idempotency key returns the same Action, a reused key with different tool/params is a 409 (keys unique per business, migration 0004); approve/reject/execute lock and re-read the Action (`SELECT … FOR UPDATE`), so a concurrent second decision sees `executed` and replays instead of overwriting it; `sandbox_*.action_id` UNIQUE rejects a second write |
| T6 | Log tampering | DB edit to hide action | Hash-chained AuditEvent + verify; append-only in ORM and DB | A5 (`test_audit.py`) | mitigated for app-level and SQL-client tampering — `hash = sha256(prev_hash + canonical_json(event))` (ASCII, strict JSON); `verify_chain` reports the first broken seq for an edited, deleted or individually re-hashed row; migration 0003 trigger rejects UPDATE/DELETE on Postgres and SQLite; appends serialized with a Postgres advisory lock. Not mitigated against a DB owner who can drop the trigger: see residual risks — Phase 7 anchors the head hash outside the DB |
| T7 | Hallucinated numbers | LLM invents figures | All numbers from engine tools; citations required | `test_citations.py`, `test_agent_runner.py`, live smoke; `test_forecast.py` | mitigated — every ForecastLine carries source_ids that resolve to real records (account/invoice/recurring_series/transaction); integer cents only; Phase 4: tool results carry integer `*_cents` plus server-formatted `*_display` text and a `ref` per record; `agent/citations.py` checks every `[[type:id]]` (known type, exists in the user's business, actually returned by a tool in this conversation) and every money/percent figure (cited in its sentence, and carried by one of those citations); one automatic rewrite, then the answer is shown with invalid chips marked and a visible "could not be verified" notice, audited `agent_citation_failed`. Residual: the check matches figures, not the meaning of the sentence around them |
| T8 | PII leakage to LLM | Account numbers/emails in prompts | `pii.py` masking before LLM calls | `test_pii.py`, `test_agent_a1.py` | mitigated — categorizer sends only normalized descriptions (card numbers, terminal IDs, phones, refs stripped) + direction, no amounts or DB ids (`test_llm_classifier.py`); Phase 4 agent: `agent/pii.py` masks IBANs, card and account numbers, emails and phones in every string of every tool result, user message and tool input (ints untouched) into per-conversation tokens; contact emails are never put in tool results; unmasking happens only on the final text shown to the signed-in user; audit payloads and stored rationales keep the masked form; the A1 test asserts QS-2291's account number never appears in any model request. Residual: regex-based, so unusual formats (e.g. spelled-out numbers) are not caught |
| T9 | Secret leakage | Keys in repo | `.env` gitignored; env-only config | CI grep check | in progress — `.env` gitignored, only `.env.example` committed |
| T10 | Abuse of chat endpoint | Spamming / cost | Rate limit per user | `test_chat_api.py` | mitigated — `POST /chat`: 10 turns per minute and 100 per day per user, counted from `agent_turn_started` audit events (durable, multi-worker safe), 429 + `Retry-After` + audited `chat_rate_limited`; one turn in flight per user; message ≤ 4,000 chars; ≤ 8 model calls per turn (the last with tools disabled), ≤ 4,096 output tokens per call; conversations are server-side only (2 h, ≤ 30 turns), so a client cannot inject forged history. Residual: the in-flight lock is per process |
| T11 | Malicious upload | Huge / non-CSV file | Size + type limits, parser sandboxed from execution | `test_csv_parser.py`, `test_api.py` | mitigated — parser enforces ≤2 MB, `.csv`, UTF-8, no NUL bytes, ≤20k rows, recognised header, all-or-nothing; stdlib `csv` only, nothing evaluated. `POST /upload` (Phase 3): owner/accountant only, reads at most 2 MB + 1 byte, rejections and ingests audited (`test_api.py`) |
| T12 | Stolen / forged session | Guessed password, forged or replayed token | bcrypt passwords; HS256 JWT with ≥32-char secret (boot refuses weaker), algorithm pinned, `exp`/`iat`/`sub` required, 8 h lifetime; unknown emails still pay a bcrypt check; passwords > 72 bytes fail normally; every attempt audited, failures keyed by HMAC(secret, email) — no reversible email in the log; 5 failures per email in 15 min → 429 lockout (audited `login_locked`), counted for unknown emails too; CORS limited to `CORS_ORIGINS` | `test_api.py`, `test_security_review.py` | mitigated — residual: lockout is per email, not per IP (an attacker can lock out a known email for 15 min); no token revocation before expiry |

## Known residual risks (be honest in the report)
- Demo auth (JWT, seeded users) is not production-grade identity: lockout is per email only (no per-IP limit, so a known email can be locked out on purpose), no token revocation before expiry (8 h).
- All seeded demo users share one known password (`seed/load.py`); demo data only.
- LLM categorization can still mislabel; mitigated by confidence threshold + human review, not eliminated.
- Forecast is heuristic (historical behavior); not a guarantee.
- Audit chain: the hash is unkeyed, so someone able to drop the trigger (DB owner) can edit any event and recompute every later hash, or delete the newest events, and `/audit/verify` still passes. Planned mitigation: Phase 7's evidence export (`python -m app.sandbox.evidence_export`) writes the latest seq + hash outside the DB; verifying against that anchor detects any rewrite or truncation before it.
- `Policy.payee_allowlist_mode` is stored but not read: the gate always behaves as `strict` (only `is_allowed_payee` counterparties), which is the safe setting.
- Financing catalog is simulated, not real offers. Every ranking carries a "not financial advice" disclaimer (`engine/financing.py`); options are suggestions only and nothing executes without an approved Action.
